# lulu-bootstrap conf 模块 — 需求文档（Requirements）

> 版本：v2（精简版）
> 日期：2026-08-12
> 范围：`d:/code/lulu-bootstrap/conf`（配置 Schema 定义与代码生成）
> 变更：相较 v1，大幅收敛配置域，仅保留核心 9 个子域，移除 AI / Broker / Registry / Script / Workflow 五大域。

---

## 1. 背景与目标

`lulu-bootstrap` 是一个**声明式应用启动器（declarative bootstrapper）**，读取一份统一配置，将 Go 应用所需的各类子系统组装成 `lulu.App`。

`conf` 模块是这套机制的**配置契约层（contract）**：用 **Protocol Buffers（proto3）** 定义 `BootstrapConfig` 及子配置的数据结构，并通过 **buf** 工具链编译为 Go 代码（`conf/gen/go/...`），供运行期解析使用。

**v2 范围收敛**：当前阶段聚焦于"最小可运行核心"，仅保留 9 个最基础子域，砍掉尚未落地或在框架外演进的子系统（AI、消息代理、注册中心、脚本引擎、工作流），以降低契约面、加快迭代。被移除的域保留后续按需回加的可能性（见 §3 待恢复域）。

**目标**：用一份强类型、可演进、跨语言友好的 Schema，统一配置来源（YAML / JSON / 二进制）。

**非目标**：
- `conf` 只负责**定义 Schema 与生成代码**，不实现任何子系统连接逻辑。
- 不引入运行期业务依赖（生成的 `gen/` 不依赖 `lulu` 或插件库）。

---

## 2. 利益相关方

| 角色 | 关注点 |
|------|--------|
| 应用开发者 | 用一份 YAML 描述应用拓扑，开箱即用 |
| 框架维护者 | Schema 向后兼容、可扩展、可生成文档 |
| 工具链 | proto 可被 buf / 文档 / 校验器消费 |

## 3. 功能需求

### FR-1 顶层配置结构
- **FR-1.1** 提供顶层消息 `BootstrapConfig`，包含 9 个子域配置字段：
  `app`、`server`、`config`、`logger`、`tracer`、`metrics`、`storage`、`cache`、`database`（字段 1–9）。
- **FR-1.2** 每个子域为单值消息；调用方决定是否填充。

> 对比 v1：已移除 `registry`(4)、`broker`(8)、`ai`(10)、`workflow`(11)、`script`(13)，原字段编号顺延重排。

### FR-2 多配置源（Config）
- **FR-2.1** 提供消息 `Config`，通过 `optional` 字段支持多种配置源（混合配置）。
- **FR-2.2** v2 仅内置 **2 种**配置源：`file`（File，本地文件 + fsnotify watch）、`nacos`（Nacos，server_addrs/namespace/group/data_id/format）。
- **FR-2.3** `file` 支持 `path` / `format`(json/yaml/toml，缺省按扩展名) / `watch`(变更监听)。
- **FR-2.4** Nacos 参数：`server_addrs`、`namespace`、`group`、`data_id`、`format`。

> 对比 v1：移除 fs / etcd / consul / apollo / kubernetes / redis / zookeeper / vault / http / env / oss / polaris。

### FR-3 传输层（Server）
- **FR-3.1** 提供消息 `Server`，通过 `optional` 字段支持多种传输协议。
- **FR-3.2** v2 仅内置 **1 种**：HTTP。
- **FR-3.3** HTTP 配置：`addr`、`driver`(net/http / chi / gin / fiber，缺省 net/http)、`tls`(统一 TLS 子消息)、`middleware`。
- **FR-3.4** HTTP 中间件（按字段顺序注册）：Recovery、CORS、Logging、RequestID、Tracing、RateLimit、Timeout（共 7 种）。
- **FR-3.5** 统一 `TLS` 子消息：支持文件方式(cert/key/ca path) 与内联 PEM(cert/key/ca bytes)，及 `insecure_skip_verify`。

> 对比 v1：移除 HTTP/3、gRPC、GraphQL、SSE、WebSocket、TCP、UDP、KCP、Thrift、tRPC、WebTransport、Cron、HPTimer、MCP、SignalR、Socket.IO、WebRTC、Asynq、Machinery，以及全部 11 种消息队列 Server（Kafka/RabbitMQ/Redis/NATS/MQTT/Pulsar/ActiveMQ/AzureSB/NSQ/RocketMQ/SQS）。

### FR-4 日志（Logger）
- **FR-4.1** 提供消息 `Logger`，含 `type` 字段（枚举，当前仅 `SLOG`）与 `optional` 引擎配置。
- **FR-4.2** v2 仅内置 **1 种**：Slog（Go 标准库）。
- **FR-4.3** Slog 配置：`level` / `format` / `output_path`。

> 对比 v1：移除 Zap、Zerolog、Logrus、Charm、Phuslu、Glog、Hclog、Fluentd、Loki、Sentry、阿里云 SLS、腾讯云 CLS、AWS CloudWatch。

### FR-5 追踪与指标（Tracer / Metrics）
- **FR-5.1** `Tracer`：`type` 枚举（仅 `OTLP`），`Otlp` 配置含 endpoint、insecure、headers(map)、sampler、sample_ratio。
- **FR-5.2** `Metrics`：`type` 枚举（`PROMETHEUS` / `OTLP`）；prometheus 含 addr/path，otlp 含 endpoint/insecure/headers/push_interval。**与 v1 一致**。

### FR-6 对象存储（Storage）
- **FR-6.1** `Minio` 与 `S3`（S3 兼容）；含 endpoint、region、access/secret key、token、use_ssl、force_path_style、bucket。**与 v1 一致**。

### FR-7 缓存（Cache）
- **FR-7.1** `Local`（FreeCache，size / default_ttl_seconds）与 `Redis`（addr / password / db / key_prefix）。**与 v1 一致**。

### FR-8 数据库（Database）
- **FR-8.1** 通过 `optional` 字段支持多种数据库。
- **FR-8.2** v2 仅内置 **2 种**：`SQL`（GORM/Ent 共用，driver/source/migrate/enable_trace/enable_metrics/连接池参数）、`Elasticsearch`（addresses/username/password/cloud_id/api_key/service_token/certificate_fingerprint/enable_metrics/enable_debug_logger/max_retries/compress_request_body/discover_nodes_*）。

> 对比 v1：移除 MongoDB、ClickHouse、Doris、OpenSearch、InfluxDB、Cassandra。

### FR-9 应用元数据（App）
- **FR-9.1** `id`、`name`、`version`、`env`、`stop_timeout`(google.protobuf.Duration)。**与 v1 一致**。

### FR-10 代码生成与工具链
- **FR-10.1** 使用 **buf v2** 管理 module（`buf.yaml`，module 路径 `protos`）。
- **FR-10.2** `buf.gen.yaml` 生成 Go 到 `gen/go`，`paths=source_relative`，`go_package_prefix = github.com/kalandramo/lulu-bootstrap/conf/gen/go`。
- **FR-10.3** 生成的 Go 包固定为 `github.com/kalandramo/lulu-bootstrap/conf/gen/go/bootstrap/v1`。
- **FR-10.4** 通过 `buf managed mode` 自动管理 `go_package`。
- **FR-10.5** 当前 `conf/go.mod`、`conf/go.sum` 已移除（改由仓库根 go.mod 统一管理依赖）。

### FR-11 配置编解码
- **FR-11.1** 运行期支持从 YAML / JSON / Protobuf 二进制（`.bin`/`.pb`）加载 `BootstrapConfig`。
- **FR-11.2** YAML 经 `yaml.YAMLToJSON` 转 JSON，再 `protojson` 反序列化。

### 待恢复域（v1 中曾定义，v2 暂移除）
以下域已从 `conf/protos` 删除，后续如需可重新引入（连同对应 builder）：
- `ai`（OpenAI / LangChainGo / Eino）
- `broker`（Kafka / RabbitMQ / Redis / NATS / MQTT / Pulsar 等 13 种）
- `registry`（Consul / Etcd / Nacos / Zookeeper / Polaris / Eureka / Kubernetes / ServiceComb）
- `script`（Lua / JS / Python / Go / WASM / CEL / Expr / Starlark / TCL）
- `workflow`（Temporal / Argo / Conductor / GoWorkflows）

## 4. 非功能需求

| 编号 | 需求 |
|------|------|
| NFR-1 | **强类型**：字段编译期可校验，避免 `map[string]any`。 |
| NFR-2 | **可演进**：proto3 + `optional`，新增字段向后兼容；保留编号不复用。 |
| NFR-3 | **可扩展**：新增域/源只需新增 `optional` 子消息 + 注册 builder。 |
| NFR-4 | **单一事实源**：`protos/` 唯一，生成 `gen/` 不手工改。 |
| NFR-5 | **跨语言友好**：基于标准 protobuf。 |
| NFR-6 | **生成代码零业务依赖**：`gen/go` 仅依赖 `google.golang.org/protobuf`。 |
| NFR-7 | **可校验**：可被 buf lint / breaking 守护。 |

## 5. 目录结构约束

```
conf/
├── buf.yaml            # buf module 定义 (v2)
├── buf.gen.yaml        # 代码生成插件与输出配置
├── protos/             # Schema 源文件（唯一事实源）
│   └── bootstrap/v1/   # package bootstrap.v1（10 个 .proto）
│       ├── bootstrap.proto, app.proto, server.proto, config.proto,
│       └── log.proto, tracer.proto, metrics.proto, storage.proto,
│           cache.proto, database.proto
└── gen/                # 自动生成代码（禁止手工编辑）
    └── go/bootstrap/v1/  # 10 个 .pb.go
```

> 对比 v1：proto 文件从 15 个减至 10 个（移除 ai/broker/registry/script/workflow）。`conf/go.mod` / `conf/go.sum` 已删除。

---

## 6. 验收标准

1. `buf generate` 在 `conf/` 成功执行，产物 `conf/gen/go/bootstrap/v1/*.pb.go`（10 个）。
2. `BootstrapConfig` 可在 YAML 声明全部 9 个子域，被运行期正确解析。
3. 任意新增配置源仅通过"新增 `optional` 子消息 + 注册 builder"，不改现有字段编号。
4. `gen/go` 不依赖 `lulu` 及其插件包。

---

## 7. 风险与假设

- **假设**：`bootstrap.v1` 为首个稳定主版本。
- **风险**：proto 删除/重排字段会破坏向后兼容 —— 移除 ai/broker/registry/script/workflow 属于破坏性收敛，需 `buf breaking` 基线对齐（建议以本次提交为新的兼容基线）。
- **注意**：顶层字段编号已重排（原 14→9），任何已落地的 YAML 需同步调整。
